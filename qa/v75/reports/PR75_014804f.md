### Cryptographic re-verification (M2) — independent, not Gemini's vectors
Gemini's own vectors were not used. I wrote a QA-owned RFC 8032 Ed25519 signer in BigInt that shares no code with `node:crypto` or the validator. I derived the 8-torsion subgroup from the curve equation and enumerated every encoding a lenient decoder might accept: canonical, sign-bit-flipped and non-canonical `y+p`.

* **Valid controls:**
  * My signer's signatures are accepted for 12 random keys through the PEM, raw-hex, base64 and KeyObject paths.
  * 60 random `node:crypto` keys are never falsely rejected.
* **Torsion keys:** all **14 encodings × 4 key paths** are rejected on the candidate. The vulnerable source accepted **56 of 56**.
* **Forgery attempts:** R drawn from 12 torsion encodings × S ∈ {0, 1, L−1} × every torsion trust-root, and none is proven.
* **Mutation:** flipping each of the 512 signature bits, and each of the 256 trust-root key bits, is never proven.
* **Malleability:** S+kL for every k that fits in 256 bits is rejected, as is R with y ≥ p.
* **Payload binding:** each of the 11 signed fields, when changed, is never proven.

## 3. Regression hunt (do legitimate inputs still pass?)

Accepted as they should be:
* TPS jitter (1,140–1,230 ticks/min above the floor).
* Signed windows padded by 3 s, padded by 10 min each side, and written with a `+00:00` offset.
* A 4 s recorder pre-roll.
* Genuine 5/10/30/59-minute claims.
* Older journals without `sourceSha`/`runId`/`citizens`.
* Idle citizens and a roster in a different order.
* A realistic gather → craft → place chain with an exact final inventory.
* Valid signed controls reach `real_minecraft` / `VERIFIED`.

Findings:
* **G1 (gate regression).** `pnpm typecheck:tools` fails on the candidate: `offline-validator-report.ts(22,24) TS2352: Conversion of type 'RunBundle' to type 'Record<string, unknown>'`. It passes on #67. The scenarios still run under `tsx`, but the repo gate is red.
* **Pre-roll asymmetry (informational).** A recorder pre-roll of 30 s or 90 s before the signed window is rejected, because the window must be within 5 s of the journal span in duration. Yet the window's *placement* is unconstrained (M1).
* **Legitimate losses (known limit).**
  * Three verified gathers with two logs legitimately deposited in a chest give a hard `UNEXPLAINED_LOSS` violation.
  * The journal vocabulary has no row for a deposit, death drop or consumption, so a legitimate loss and a forged gather are indistinguishable. The validator chose violation.
  * That is acceptable for the offline scripted flow (no deposits). It will reject legitimate **live** runs once citizens deposit items, so loss evidence must be added before live use.

## 4. Remaining bypasses and issues (each has a named reproduction `[QA75-xx]`)

| ID | Sev | Bypass |
|---|---|---|
| **M1** | Medium | **Signed window placement is unconstrained.** The check is only "overlaps" and "duration ≥ span − 5 s". A window shifted **30 minutes** later, or overlapping only the journal's **final second**, reaches `real_minecraft` / `VERIFIED`. |
| **M2** | Medium | **`journalRows` need only be a subset of the signed raw lines.** Omitting a signed ghost-citizen action, or a signed conflicting second start row, from `journalRows` makes `PHANTOM_CITIZEN_ACTION` and `SOURCE_IDENTITY_CONFLICT` vanish: `VERIFIED` / `real_minecraft`. |
| **M3** | Medium | **Only a few fields are bound to the raw lines.** Smoothing a genuine mid-run tick regression in the parsed `serverGameTick` values makes an honest `offline_simulated` result become `real_minecraft`. Editing an observation's `position` turns a failed move into a `VERIFIED` move. |
| L1 | Low | A forged first observation with a non-empty `beforeInventory` (40→41) while the physical final inventory is 1 is not flagged, because continuity starts at the second observation and the last `after` is not compared to the final inventory. |
| L2 | Low | `mode` can read `real_minecraft` while the same report carries ERROR violations (for example `ROSTER_CONFLICT`). `overallStatus` is correctly `VIOLATIONS_DETECTED`, but a consumer reading `mode` alone is misled. |
| L3 | Low | `trustedAuthorities: []` behaves as "trust every key in `trustedKeys`". |
| L5 | Low | CLI with `--manifest` prints `VERIFIED` for the simulated sample fixture, as on #67. `mode` and the human note disclaim it. |

Constraints on exploitability:
* **Reach.** M1–M3 need a *genuinely signed* raw journal plus caller-controlled parameters or rows. The shipped CLI and offline pipeline derive rows from one file and never receive a trust root, so no shipped path is exploitable today. The risk is the library API as the future live gate.
* **Performance.** The raw-row binding is O(n²): 20,000 rows validated in 2.1 s. Not a problem at this scale.

## 7. Correction instructions
1. **G1:** cast through `unknown` (or type the bundle) in `tools/v1-integration/offline-validator-report.ts:22`, and keep `typecheck:tools` in the PR's checklist.
2. **M1:** require the signed window to contain the journal's first and last `at` (± a small, documented skew), not merely overlap.
3. **M2 / M3:** derive all validator inputs from `rawJournalLines`. At minimum, assert row count and identical canonical JSON for every row, not a subset on selected fields. Reject any `journalRows` that omit a signed row.
4. **L1:** start continuity at the manifest's empty inventory, and compare the last `afterInventory` with the physical final inventory.
5. **L2:** set `mode` to `real_minecraft` only when there are no ERROR violations.
6. **L3:** treat an empty `trustedAuthorities` as "none trusted" (or reject it).
7. **L5:** apply the NOT_PROVEN cap whenever `mode` is `offline_simulated`, with or without a manifest.
8. **Before live use:** add explicit loss rows (deposit, craft, eat, death) so legitimate losses stop looking like forgeries; add CI for the validator and for `qa/v67`; add Linux/Windows.
